# FI9 prospective validation protocol

**Purpose.** Historical results (A and B) have all been seen during development. Only forecasts registered before their outcome is published are untouched evidence (category C).

## Locked procedure

1. Each quarter, on the scheduled issue date (last day of its second month), or earlier if the previous quarter's SWS result is already out, run `python -m app.fi9.serve issue`. Then run `python -m app.fi9.audit run` and `python -m app.fi9r.audit run`.
2. `serve issue` appends one record to `backend/data/fi9/out/prospective_register.jsonl` with:
   * issue date and target quarter;
   * model version and artifact sha256;
   * training cutoff and latest input publication date;
   * probability, class, projected level and interval;
   * baselines (naive persistence, climatology/always-LOW) and the local-level challenger;
   * a generation timestamp, and its own and the previous record's sha256.
3. Records are never edited. `python -m app.fi9.prospective verify` checks the hash chain. A re-issue for the same target is appended as a revision and **not scored**. Only the first forecast per target counts.
4. When the target quarter's SWS result is published, run `python -m app.fi9.prospective score`. It writes `prospective_scores.json`: class, Brier, interval coverage, and the same for each baseline.

## Adoption and reliability requirements (prospective)

* No reliability claim before **12 scored forecasts including at least 3 HIGH quarters** (about three years).
* At that point FI9 may be called reliable for Lead 1 only if, on the prospective forecasts:
  * it passes the FI7 reliability rule;
  * its Brier is not worse than naive persistence;
  * its interval covers at least 80 % of outcomes.
